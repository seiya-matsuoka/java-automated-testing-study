# Codex 移行に伴う学習コンテキスト引き継ぎ

## 1. 本ドキュメントの目的と位置づけ

本書は、`java-automated-testing-study` の学習・教材生成を ChatGPT のチャット中心の運用から Codex によるワークスペース内の作業へ移行する際の引き継ぎ資料である。  
これまでのチャットでのやり取りを Codex が自動的に参照できることは前提とせず、既存のリポジトリだけでは伝わりにくい背景、品質基準、最終的に採用した判断、移行時の注意事項を補完する。

本書は、新しい学習カリキュラムやアプリケーション仕様を定義するものではない。  
学習範囲、技術的な要件、既存の作業運用は次の文書を正本とする。

| 文書                                                                | 正本として扱う情報                                                                    |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| [`learning-curriculum.md`](planning/learning-curriculum.md)         | 学習目標、Unit 01〜11 の学習範囲、各 Unit の到達点                                    |

リポジトリ固有の `AGENTS.md` は、本書とは別に作成する予定である。

本書は、移行時点までに確定した方針を記録する。  
既存のコードや計画にない具体的な実装内容を、過去に合意済みだったかのように補わない。

## 2. これまでの学習経緯と現在の進捗

### 学習の背景と狙い

Java / Spring Boot の開発経験を土台に、自動テストについて体系的に学習するためのリポジトリである。  
テスト技術を単発のサンプルで暗記するのではなく、同じ注文管理 REST API に対してテストの対象・境界を段階的に広げ、何をどの範囲で保証するのかを理解することを重視する。

学習は完成済みの Production Code・Test Code のコードリーディングを中心とする。  
学習者自身が後からテストを書き足さなければ主要項目を理解できない構成にはしない。  
学習した技術を構文だけでなく、理由、設計判断、実務との関係まで把握することを目指す。

**Unit 01〜05 は生成・確認・学習のすべてが完了している。次に着手するのは Unit 06 である。**

## 3. 学習方法と生成工程の実際の運用

### コードリーディング中心の学習

基本的な流れは `learning-operation.md` に従う。  
README で概念を理解し、Production Code の責務を確認してから対応する Test Code を読み、Fixture、SUT、Test Boundary、Assertion / Verification を把握し、実行結果を確認する。

**最初から自力で大量のコードを記述することは、今回の正式な学習工程の前提ではない。**  
コードリーディングに適した教材を完成状態で用意し、動かして確認しながら理解する方針を継続する。  
自主的な追加実装や改変は可能だが、その余地を残すために重要なケースを未実装にしない。

### 1 Unit を必ず 2 工程に分ける

**第1回：`README.md` 以外の必要な成果物を完成させる。**  
Test Code、必要な Production Code・Fixture・設定・SQL・補助教材などを、その Unit の学習に必要な範囲で作成する。  
ユーザーが内容を確認し、必要な修正を行った後、次の工程へ進む。

**第2回：第1回で確定した実装に対応する Unit README を作成する。**  
クラス・メソッド・テストケース・設定・実行方法と説明を一致させる。  
第2回の依頼を理由に、第1回で確定したソースコードまで独断で変更しない。

```text
第1回：実装・設定・Test Code・Fixture など
    ↓
検証・レビュー・必要な修正
    ↓
第2回：実際の成果物に対応した Unit README
    ↓
README の確認・必要な表現修正
    ↓
当該 Unit の学習・完了
```

**第1回の完了をもって、第2回や次 Unit を自動で開始しない。**  
計画だけの依頼、内容確認だけの依頼、コードの修正依頼、README の修正依頼を区別し、指示された範囲だけを作業する。

### Codex 移行による変更点

従来は ChatGPT が差分 ZIP を作成し、ユーザーがリポジトリへ反映していた。  
Codex では、許可されたワークスペース内の実ファイルを直接編集する運用へ切り替える。  
**変えるのは成果物の受け渡し方法であり、2 工程の区切り、レビュー、内容確認、品質基準は変えない。**

`learning-operation.md` の ZIP 受け渡しの記述は、移行前の運用として残っている。  
この差異は移行に伴う運用上の更新事項として扱い、既存の計画ドキュメント全体を無断で書き換える理由にはしない。  
リポジトリ固有の `AGENTS.md` と着手時のユーザー指示で、直接編集の運用を明確にする。

作業時には既存ファイルの変更差分を確認し、変更・追加したファイルとその目的を報告する。  
未依頼のファイル整理、命名変更、既存コードの大規模修正を同時に行わない。  
Git・GitHub 操作や外部通信・依存追加などの承認境界は、グローバルおよびリポジトリ固有の `AGENTS.md` とユーザー指示に従う。

## 4. ソースコード・テストコードの品質基準

### Unit の目的に合わせて教材の完成度を確保する

実装量を一律に小さくするのではなく、各 Unit の学習内容を理解するために必要な代表ケースを、十分なバリエーションを持って完成させる。  
正常系だけでなく、テーマに関係する異常系、境界条件、状態遷移、依存先の障害、DB / HTTP の振る舞いなどを必要に応じて含める。  
一方、実業務の全パターンを網羅することや、学習目的を超える機能を追加することは要求しない。

- 意図的な TODO、空の Test Method、未完成の Fixture、必要な Assertion の省略を残さない。
- Production Code と Test Code の責務・テスト境界を明確にし、既存アプリの業務仕様を根拠なく変更しない。
- Test Fixture、Test Double、DB・HTTP の依存先は、何を制御し、何を本物として検証するかが分かるようにする。
- 学習対象に合わせて必要なファイル・テスト数は変えてよい。以前の Unit のファイル数やテスト数に合わせる必要はない。
- 既存のコードの命名、Java / Spring Boot / Maven の慣習、リポジトリ構成を尊重する。

### 日本語コメントの役割と粒度

Unit 03 では、テストコードのコメントの丁寧さ・説明対象を調整した最終修正版が採用された。  
その後の Unit 04・05 でも同じ方針を継続している。  
**コメント量を減らす方向へ戻さず、学習者がコードの意図を追える説明を適切に残す。**

特に、次の情報をコードに即して説明する。

- クラス・メソッドの責務と、この Test Case を設けた理由。
- Fixture や Test Data がどの条件・業務状態を再現しているか。
- Arrange・Act・Assert、および stubbing・verification のうち学習上重要な処理の意味。
- Mock / Stub / Fake / Spy、real dependency、Spring Test Slice、DB、外部 HTTP API などを選ぶ理由とテスト境界。
- Assertion がどの仕様・状態・副作用・禁止される操作を保証しているか。
- Spring Annotation、Transaction、JDBC / SQL、Row Mapping、HTTP request / response 等、コードだけでは読み取りにくい仕組みや設計上の判断。
- 誤解しやすい制約、前提条件、例外や失敗時の扱い。

処理をそのまま日本語に置き換えるだけのコメントは避ける。  
同時に、単純なコメント削減を目的に、Fixture の意図や確認対象の説明まで取り除かない。  
実装と食い違う説明や、実際には保証していない条件を「保証している」と記載することも避ける。

Production Code についても、メインの学習対象がテスト技術だからという理由で説明を省略しない。  
Java / Spring Boot / SQL に関する必要な背景をコメントで補い、README とコードコメントを相互補完させる。

## 5. Unit README の品質基準

### 最優先は学習範囲の網羅性と理解の深さ

各 Unit の学習範囲に含まれる重要な用語・概念・考え方を、実装例に直接現れるかどうかだけで選別せず、必要な範囲で説明する。  
単なる用語一覧や API の紹介で終わらせず、何を意味するか、なぜ必要か、何を解決するか、類似の方法との違い、実務での位置づけ、今回の教材との関係までつなげる。

**文章量・行数・コードブロック数には一律の上限や目標値を設けない。**  
単元の複雑さや教材数に伴って README が長くなっても問題ない。  
一部の説明の重複は、各セクションの役割を果たしている限り許容する。  
文字数を削ること、重複をゼロにすることを理由に、必要な説明を省略・簡素化しない。

README は学習内容を体系的に理解するための文書であり、コードコメントは各実装箇所の意味を理解するための説明である。  
README に任せることを理由にコードコメントを薄くしたり、コードに書いてあることを理由に README の概念説明を省略したりしない。

### セクションごとの役割と説明の流れ

共通の見出し・役割は `learning-operation.md` の第7章を正本とする。  
特に重要なのは、**正しい見出しへ配置するだけでなく、その中で自然に理解が進む順序へ説明を組み立てること**である。

| セクション             | 実際の記載で重視する役割                                               |
| ---------------------- | ---------------------------------------------------------------------- |
| この Unit の目的       | Unit 全体の狙いと前後の学習との関係を簡潔に示す                        |
| 学習内容               | 用語・概念・理由・比較・実務上の考え方を丁寧に説明する中心項目         |
| 使用する技術・ツール   | 実際に使うフレームワーク・ライブラリ等と、その Unit での具体的な役割   |
| テスト対象とテスト境界 | SUT、本物として動かす範囲、Test Double、起動する／しない依存先         |
| 使用するファイル       | 追加・変更ファイル、参照する Production Code、実在する相対リンク       |
| 前提                   | 既習事項・準備済みの知識。今回初めて扱う重要事項を前提扱いで省略しない |
| コードリーディング     | 実際のクラス・メソッドを、何を見るためにどの順で読むか案内する         |
| 実行・確認             | 実行コマンド、必要環境、期待される確認対象、結果・失敗の読み方         |
| 学習ポイント           | Unit を通して得る本質的な考え方、他の場面でも使える判断基準            |
| 補足                   | 本筋を助ける比較、注意点、対象外・後続 Unit との関係                   |

学習内容を補足へ押し出しすぎたり、コードリーディングに概念説明を集中させたりしない。  
逆に、セクション間に少し重複が生じることを過度に気にして重要な説明を削らない。  
**概念の導入 → 違いと判断の理由 → 実装における位置づけ → 実コードの確認 → 実行・結果の理解**が無理なくつながるようにする。

第2回の README は、必ず第1回の確定済み実装を読み直して作成する。  
ファイル名、テストメソッド名、Fixture、実行コマンド、実行環境、テスト境界を想像で補完しない。  
環境上実行できない項目は、検証済みであるかのように記載せず、未確認事項を明示する。

## 6. Markdown・文章表現の方針

### 文体・用語

日本語の技術文書調の言い切りを基本とし、過度に会話的・装飾的な表現を避ける。  
英単語・技術用語と日本語の間には、読みやすさを考慮して原則として半角スペースを入れる。  
クラス名・メソッド名・パス・コマンドなどの識別子は原文の表記を維持し、必要に応じて code span を用いる。

### 改行と空行は意味に応じて使い分ける

このリポジトリでは、これまで確定した Unit 01〜05 の README と計画文書の自然な段落感を継続する。  
**空行の削減や追加を目的に機械的な整形を行わない。**

- 同一の段落・連続する説明で、表示上も改行したい箇所は、行末の半角スペース2つによる Markdown 改行を使う。
- 意味・論点・説明のまとまりが変わる箇所には空行を入れ、自然に段落を分ける。
- 同じ段落でも常に強制改行する必要はなく、文脈と読みやすさを優先する。
- 見出し、箇条書き、表、コードブロックの前後は Markdown の構造として適切な空行を設ける。
- 空行を使うこと自体は問題ではない。全ての箇所を空行にすることも、逆にほとんどの空行を消すことも避ける。

なお、ユーザーが共有したグローバル `AGENTS.md` では、通常の説明文に対して行末半角スペース2つを原則使用しないルールになっている。  
**本リポジトリの Markdown では、上記の既存プロジェクト固有ルールを優先する**方針である。  
この相違は、別途作成するリポジトリ固有の `AGENTS.md` にも明記する。

### 文章・表・コードブロックのバランス

文章だけで読める箇所を無理にコードブロックへ変換したり、コードブロックの数を増減させること自体を目標にしない。  
一方、手順、処理の流れ、Test Boundary、概念の対比、状態遷移などは、`text` コードブロックや表で整理した方が理解しやすい場合がある。  
普通の文章、箇条書き、表、`text` / `java` / `bash` 等のコードブロックを、**学習しやすさと技術文書としての自然さ**で選択する。

各 Unit の README は、図示の形式を統一するための資料ではなく、読み進めて理解を深めるための資料である。  
Unit 03 と Unit 04 の最終版を、説明と視覚的整理の両方の参考例とする。

## 7. これまでの修正から確定した注意事項

### Unit 03：説明内容の保持と改行・空行

Unit 03 では、README の詳細な初期版から構成・段落を修正する過程で、説明の削除・過度な簡素化や、空行の機械的削減が問題になった。  
その結果、次の基準が明確になった。

- 最初に必要と判断した十分な概念説明を、見た目や文字数の調整を理由に失わせない。
- 各セクションの役割に沿って配置し、移動後の文章の前後関係も自然になるよう確認する。
- 説明文の内容を確定した後の「改行・空行のみ」の依頼では、内容・見出し・構成・コード例まで変更しない。
- 空行の一括削除や一括置換ではなく、段落として成立するかを文脈ごとに判断する。

最終的に採用したのは、詳細な説明を保持し、適切な配置と自然な改行・空行を両立した Unit 03 README である。  
**失敗を避けるために短くするのではなく、内容と表現をそれぞれ適切に整える。**

### Unit 04：表現方法の小規模な調整

Unit 04 では、README の内容・説明粒度は承認された一方、「学習ポイント」「補足」で `text` コードブロックによる視覚的整理が以前の Unit より少なかった。  
そこで、説明内容や章構成を変更せず、概念の対比が効果的な**5か所に限定して**表現を調整した最終版が採用された。

この経緯から、次を確定事項とする。

- 文章とコードブロックのどちらかへ一律に寄せない。
- 読者にとって違いが分かりやすくなる箇所だけ表現を工夫する。
- 小規模な表現修正を、大規模な再構成・概念追加・内容削減へ拡大しない。
- 表現に必要な軽微な文言調整は可能だが、学習内容・意味・説明の深さを変えない。

### 以後の修正に共通する原則

**依頼された修正範囲を厳密に守る。**  
誤字修正、コメントの増強、改行の調整、README の表現改善、機能実装など、目的の異なる作業を混同しない。  
すでに確定したコード・文書の未依頼部分は、原則として変更しない。

内容変更が必要と判断される場合も、依頼された表現修正に紛れ込ませず、必要性と影響範囲を区別して報告する。  
最終版が承認された Unit を、後続 Unit の生成に合わせて無断で書き換えない。  
完成後には変更差分を見て、修正対象外の内容や構造が意図せず変わっていないか確認する。

## 8. Unit 06〜11 の継続方針

### カリキュラムを正本とし、細部を勝手に確定しない

Unit 06〜11 の学習目的・主な学習内容・テスト対象は、`learning-curriculum.md` の第12〜17章に記載済みである。  
チャット上では、これらに対する具体的なテストクラス名・テスト件数・Fixture 値・実装順序まで個別に確定していたわけではない。  
したがって、そのような詳細を過去の合意事項として扱わない。

ただし、各 Unit で必要な教材を十分な完成度で用意し、学習範囲の抜けを防ぐという共通方針は、Unit 06〜11 でも変わらない。  
後続 Unit では技術構成が複雑になるが、それを理由に README の説明やソースコードのコメントを薄くしない。

### 今後の Unit で継続して意識するつながり

| Unit                                    | 継続して重視する学習上のつながりと判断                                                                                                                                                                        |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 06 SQL・Repository・DB Integration Test | Unit 03 で Mock にした Repository 自身を、実 SQL と PostgreSQL で確かめる。`@JdbcTest`、Testcontainers、Fixture・Cleanup・Transaction・Constraint を扱い、H2 や DBUnit はカリキュラム上の位置づけを区別する。 |
| 07 Spring Boot Integration Test         | Unit 03 の Service Unit Test と比較し、Spring Context、実 Repository・DB、複数更新、Rollback を含む広い境界を確認する。                                                                                       |
| 08 外部 HTTP API のテスト               | Mockito による Java Object の置き換えと、WireMock による HTTP 境界の置き換えを区別し、正常系・異常系・不正 response と request verification を扱う。                                                          |
| 09 REST API 全体のテスト                | Unit 05 の Web Slice Test と異なり、実 HTTP、Controller〜DB、WireMock までの広い経路を確認する。REST Assured、DB 最終状態、正常・異常 response の確認を重視する。                                             |

| 11 CI による自動テスト                  | Unit 01〜10 の Test Suite を GitHub Actions で再現し、Testcontainers、Coverage、Artifact、Log、Matrix の役割と失敗時の読み方を学ぶ。CD / Deployment は対象外とする。                                          |

上表は、既存カリキュラムの補完として「何と比較して理解するか」を整理したものであり、新しい実装仕様や追加の必須テスト数を定めるものではない。

### 各 Unit の着手時に決めること

Unit の実装に着手する際は、既存仕様と関連する実装を確認したうえで、必要な Test Case、Fixture、依存ライブラリ、テスト境界、実行環境を具体化する。  
重要な学習項目を欠落させない範囲で、代表ケースの組み合わせや内部ファイル構成は Unit の性質に応じて判断する。  
新たな依存関係、外部通信、DB 操作、GitHub Actions の導入などは、その時点で適用される承認ルールに従う。

例えば Unit 06 では、Repository と実 PostgreSQL の Test に必要な環境・依存関係・DB 初期状態の扱いを、`pom.xml`、既存の DB Script、Repository 実装を確認してから具体化する。  
カリキュラムにない任意の技術を学習対象へ追加したり、予定されている重要概念を勝手に削除したりしない。

## 9. Codex への移行と作業再開時の確認事項

### 初回は認識合わせを先に行う

Codex で最初に行うのは、Unit 06 の実装ではなく、**既存のリポジトリと本書を読み、現在地と作業方針を整理すること**である。  
内容確認・引き継ぎ確認の依頼は、ファイルを編集する許可としない。

初回に確認する対象は、少なくとも次のとおりとする。

1. 現在のワークスペース、branch、`git status`、既存の変更。
2. グローバルおよびリポジトリ固有の `AGENTS.md` の適用内容。
3. `docs/planning/` の3文書と本書の役割・整合性。
4. Unit 01〜05 の README、既存 Production Code・Test Code、Unit 04 の補助教材。
5. Unit 05 まで学習完了・Unit 06 未着手という進捗の認識。ただしローカル実ファイルの状態に差があれば報告する。
6. 2工程生成、品質・コメント、Markdown、Git・承認、直接編集への運用変更の理解。

確認結果は、事実と未確認事項を分けて簡潔に報告し、重要な相違があれば実装前に確認する。

### Unit 06 の開始以降

認識がそろった後、ユーザーから明示的な依頼を受けて Unit 06 第1回の実装・設定・Test Code の作成へ進む。  
第1回の結果を確認してから、第2回の README を別の依頼として作成する。  
その後も同じ流れで Unit 11 まで進める。

Codex が実際のファイルを扱うため、実装後には可能な範囲でテスト・ビルド等を実行し、**実施できた検証と、環境・権限・通信制限などで未実施の検証を明確に分ける**。  
特に DB Test や CI では、必要な環境があることや実際に成功したことを推測で報告しない。

Git の staging・commit・push、branch 操作、PR 操作などは、ユーザーが明示的に依頼しない限り実行しない。  
依存関係の追加、外部通信、永続データへの変更、エージェント設定の変更なども、適用される承認ルールに従う。

### 移行準備の残作業

本書の作成後、次の作業が予定されている。

1. 共有されたグローバル `AGENTS.md` と、過去の小規模開発用のリポジトリ固有 `AGENTS.md` を参考に、本リポジトリ専用の `AGENTS.md` を作成する。
2. 本書と `AGENTS.md` をワークスペースへ配置し、Codex の初回認識合わせ用プロンプトと、その後の Unit 06 開始用プロンプトを準備する。
3. Codex で実際の状態・方針を確認し、ユーザーの指示に従って学習を再開する。

本書だけでエージェントへの移行準備がすべて完了したと扱わず、リポジトリ固有の `AGENTS.md` と初回の認識合わせを経て作業を開始する。
